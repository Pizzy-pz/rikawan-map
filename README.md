# rikawan-map — 配達先店舗ナビゲーター（store-route-navigator）

アルバイト先の酒屋（リカーショップワン）の配達業務を効率化するために個人制作した Web アプリです。
スタッフの口頭伝達とメモ頼りだった店舗情報管理をデジタル化し、**現在10名のスタッフが実業務で継続利用しています。**

🔗 **デモサイト**: https://rikawan-map.vercel.app/login

## 主な機能

| 機能 | 説明 |
| --- | --- |
| 店舗一覧・検索 | 登録した店舗を一覧表示。名前でリアルタイム検索ができます |
| 店舗登録・編集 | 店名・メモ・座標を登録できます |
| 地図・ルート表示 | 店舗詳細で Google マップを表示し、現在地からの徒歩ルートをアプリ内で確認できます |
| 店舗シェア | 自分の店舗をパブリックリストに公開できます。一括シェア・一括取り消しに対応しています |
| 新規店舗の発見 | 他のユーザーが共有した店舗を一覧から選んで自分のリストに追加できます |
| 一括削除 | 複数店舗をチェックしてまとめて削除できます |
| ログイン認証・セキュリティ | メールアドレス＋パスワードでログイン。RLS（行レベルセキュリティ）により、他ユーザーのデータには DB レベルでアクセスできません |

## 使用技術

### Next.js (App Router)

フロントエンドと API ルートを1つのリポジトリで管理できるため、別途バックエンドサーバーを立てる必要がなく、個人開発に向いていると判断しました。
Vercel との親和性の高さも選定理由のひとつです。

### TypeScript

店舗データとして店名・緯度経度・メモなど複数の項目を扱うため、型を定義して画面側と DB 側のデータの不整合を防ぐことを目的に採用しました。

### Supabase（PostgreSQL）

Firebase と比較した上で採用しました。
RLS（Row Level Security）による行単位のアクセス制御が SQL レベルで記述できるため、「自分のデータしか見えない」という要件をデータベース層で保証できます。
Firebase は SDK 経由のルール管理が中心で、DB 側での行レベル制御が難しいため、今回は Supabase を選択しました。

### Google Maps API

店舗の地図表示とルート案内のために使用。
API キーをクライアントに直接渡さず、Next.js の API Routes をプロキシとして挟む構成を採用しました（詳細は後述）。

### Tailwind CSS

ユーティリティクラスを組み合わせるだけで実装できるため、CSS ファイルの管理コストを下げつつ、モバイル・デスクトップ両対応の UI を効率よく実装できました。

### Vercel

GitHub と連携することで、push のたびに自動デプロイが走ります。フィードバックを受けてから修正→確認までのサイクルを短く保てました。

## 背景・こだわり

### 解決したかった課題

配達先の多くは Google マップに掲載されていない雑居ビルや看板のない小売店です。
入口が路地裏にある、ビルの何階かを口頭で覚えるしかない、といったケースが珍しくありません。

以前は店舗情報をスタッフの口頭伝達や個人メモに頼っていたため、**新人スタッフが常連店舗のルートを覚えて独り立ちするまで約3ヶ月かかっていました。**
曜日によって注文のある店・ない店が異なり不確定要素が多いことも、習得を難しくしていた要因です。

「自分の不便とお店の抱える課題を、自分でなんとかしたい」という気持ちで開発をはじめ、現在は **1店舗 10名のスタッフが実業務で継続利用しています。**

### 技術的なこだわり

**① Google マップに載っていない店舗への対応**

住所文字列ではなく緯度・経度の座標でピンを管理する方式を採用しました。
Google マップの検索に引っかからない店舗でも正確な場所を登録でき、路地裏の入口や雑居ビルの搬入口を直接ピン指定できます。

**② API キーのブラウザ露出防止（プロキシ構成）**

Google Maps API・Geocoding API の API キーをブラウザに渡さず、Next.js の API Routes をプロキシとして挟む構成にしました。
クライアントが直接 Google API を叩かないため、開発者ツールからキーが取得されて不正利用（課金詐欺）されるリスクを排除しています。

**③ DB レベルのデータ保護（RLS）**

Supabase の RLS（行レベルセキュリティ）を DB に設定し、ログインユーザーが自分のデータにしかアクセスできない制御をデータベース層で実現しました。
クライアント側のフィルタリングだけに頼ると、バグや悪意ある操作でデータが漏洩するリスクがあるため、DB 側で防御線を引くことを優先しました。

**④ レート制限による API 不正利用の防止**

同一 IP アドレスから1分間に30リクエストを超えた場合はブロックする仕組みを実装しました。
現在はインメモリ（Map）方式で実装しており、サーバーレス環境では複数インスタンス間でカウントが共有されないという制約があります。
この制約は把握しており、ユーザー数増加時は Redis（Upstash など）への移行を検討しています。

**⑤ バリデーションの二重実装**

フロントエンドでの入力チェックに加え、API ルート側でも同等のバリデーションを行っています。
フロントを迂回した直接リクエストにも対応できる構成にしています。

## 今後の展望

現在は1店舗での運用ですが、同社は酒類小売の系列店を**全国に展開**しており、まず**京都府内の系列店舗への導入**を目指して営業活動を進める予定です。

| 計画 | 内容 |
| --- | --- |
| **他店舗への展開** | 各店舗が独立したデータを持ちつつ、必要に応じて店舗間で情報をシェアできる構成はすでに実装済み。京都府内の系列店舗への横展開を進める |
| **研修用機能の追加** | 新人スタッフが配達先を事前に確認・学習できるモードを追加し、「口頭伝達に頼ることなく独り立ちできる」仕組みを目指す |
| **API コール数を用いたスケーリング計画** | Geocoding / Directions API のコール数を計測・分析し、ユーザー数・店舗数が増加した場合のコスト試算とレート制限の適正値を算出する。これをもとに Redis 移行のタイミングや Google Maps Platform の課金プランを判断する |
